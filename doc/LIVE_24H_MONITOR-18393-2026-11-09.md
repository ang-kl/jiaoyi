# Twenty-four-hour strategy monitor

№18,393 §§1–8 · 09-11-2026 11:15:17 SGT · by Codex (GPT-6; effort not exposed)

## TLDR

A deterministic monitor runs in the existing `jiaoyi-engineering` service. It reads four accounts and eight core symbols, writes twelve checkpoints on the persistent volume and exposes authenticated JSON and JSONL endpoints. It does not invoke a model, consume an engineering session, send Telegram, place orders, change positions or restart the trading service.

The monitor starts its clock on its first enabled execution. Its live status endpoint is the authority for the actual start, next checkpoint and completion. It must not be described as active merely because this file is merged.

## §1. Read or download a checkpoint

Use the existing owner username and password (`owner`, configured privately as `JIAOYI_UI_PASSWORD`).

- Latest saved checkpoint and run status: https://jiaoyi-engineering-production.up.railway.app/owner/live-monitor
- Download the twelve periodic records: https://jiaoyi-engineering-production.up.railway.app/owner/live-monitor.jsonl
- Fresh on-demand snapshot: https://jiaoyi-engineering-production.up.railway.app/owner/live-monitor/once

These endpoints are private and uncached. Missing credentials refuse access; they do not expose financial data through the engineering health endpoint. The public engineering status contains scheduling metadata only.

Repository CLI:


The local CLI reads its environment; it does not inherit Railway secrets. `--since` accepts an aware ISO timestamp for a standalone on-demand ledger. Without an existing local run or `--since`, the on-demand ledger starts at that invocation, which is a new baseline, not the remote run's cumulative history. Use the deployed owner endpoint for the active Railway run.

## §2. Schedule and persistence

The twelve periodic checkpoints occur at start + 0, 2, 4, …, 22 hours. A separate completion snapshot at +24 hours covers the final two hours without inventing a thirteenth periodic checkpoint. The latest endpoint returns that completion after the run ends.

Railway paths for the default run:

```text
/data/private/monitor-18393/18393-20261109/plan.json
/data/private/monitor-18393/18393-20261109/docs/live_monitoring_24h_log.jsonl
/data/private/monitor-18393/18393-20261109/completion.json
```

The plan is frozen before the first read. A file lock, indexed records, atomic replacement and fsync prevent duplicate checkpoint appends after restart. A restarted container retains the original clock. Missed intervals are marked as missing observations; current data is never backdated to fill them. A changed duration requires an explicitly new run identity.

No PR is created for each checkpoint. Records remain on the existing volume, bounded to the scheduled count, with a five-MiB log limit. On-demand reads do not advance or append to the periodic schedule.

## §3. What the figures mean

| Field | Evidence and limitation |
|---|---|
| Connected and unpaused | Four account observations with explicit connection/freshness coverage. Unavailable evidence cannot produce a success. |
| Actual dispatch latency | `null`: the deployed engine does not persist completed socket-write timestamps. The monitor does not relabel broker-fill latency as dispatch latency. |
| Touch to final guard | Separate measurement from an identity-matched successful writer receipt and original touch. It ends before socket writing. |
| Entry/refusal counts | Exact confirmed persisted subsets, distinct account/order identities, with partial fills and uncertain outcomes separated. All-stage refusal totals remain unknown where pre-intent failures lack complete identities. |
| FX/minimum-volume errors | Confirmed evidence is classified separately from legitimate risk or margin refusals. No recorded error is not proof that all stages were observed. |
| Closed trades and cash | Full owned position lifecycles, recorded broker fees and history coverage. Position-lifetime net, interval-booked cash and whole-account cash are distinct. Incomplete evidence stays null. |
| Unrealized money | Only an explicitly measured, fresh and complete broker snapshot qualifies. Stop risk or equity is not substituted for floating P&L. |
| Latest twenty | Existing official strategy/account assessment, including age and coverage. Historical policy mixtures do not certify the newly deployed policy. |
| Symbol state | Separate account states under every symbol. Mixed states, missing opening data, unavailable evidence and expired arms remain explicit. A profitable close is not automatically labelled a target hit. |

All account identifiers, source times, coverage limitations and notable changes are retained. The project goal remains at least 73% net wins over the latest twenty complete positions per strategy/account, with risk:reward 1:1.38. Monitoring does not establish a financial pass or itself improve predictive performance.

## §4. Time and source budgets

Fresh `--once` and `/once` requests use a 4.2-second collection budget, keeping the response below five seconds in the measured CLI check. A slow or failed source yields a partial snapshot with explicit errors. The existing production `/health` endpoint measured approximately 5.9 seconds, so a strict five-second fresh request may lack its data.

Scheduled checkpoints allow up to twelve seconds for the same bounded concurrent reads; database work remains capped at 3.5 seconds in a read-only transaction. The latest saved checkpoint endpoint returns immediately and retains the actual source timestamps. There is no continuous market polling added by this monitor between scheduled checkpoints.

Source threads are daemon workers with one active slot per source. A hung source cannot prevent CLI exit or accumulate new worker threads every interval. TLS verification stays enabled, redirects carrying secrets are refused, and remote errors do not expose credentials or response bodies.

## §5. Deployment boundary

Only the engineering image is updated. The reusable package lives in `ops/engineering/monitoring/`; `ops/monitoring/live_24h_monitor.py` is its repository CLI. The engineering image already contains PostgreSQL's client.

Configure on `jiaoyi-engineering` only:

```text

LIVE_MONITOR_RUN_ID=18393-20261109

JIAOYI_UI_PASSWORD=${{jiaoyi.JIAOYI_UI_PASSWORD}}
```

These are Railway references to existing credentials, not new secrets pasted into chat. Fixed read-only SQL is the only database capability used. The coordinator's existing child-environment allowlist excludes production and monitor credentials from model processes. Existing engineering jobs and pre-existing report schedules remain separate; this routine adds zero AI sessions and zero Telegram messages.

The owner selected endpoint/JSONL delivery. This chat has no callable scheduler for unsolicited two-hour chat messages. A checkpoint can be pasted into Gemini or returned here when requested; the Railway schedule continues independently of the MacBook and app.
